# 评测证据与口径

ResolveFlow AI 将三类证据分开评估，不用一个“准确率”代表整个 Agent：

1. **意图识别：** 用户请求是否被归入正确业务意图；
2. **Agent 调用链：** 是否选择正确 Agent，并按预期调用工具、传参、维护状态和进入安全分支；
3. **回复质量：** 用户回复是否相关、准确、完整、可执行，且没有暴露内部推理与原始数据。

## v2 失败归因与修复后回归

首次结果产生后，v2 立即转为回归集。本轮没有修改任何冻结用例，而是修复了以下共性问题：

- “没有这些危险情况”等安全否定改写可正常推进状态机；
- 黑屏、无画面等跨品类表达统一落入显示故障类别；
- “步骤都完成但还是没有声音”可保存排查完成与问题持续的多轮状态；
- 维修、换货和配件工单的明确确认表达可执行，拒绝表达明确写入未建单状态；
- 质量投诉在资料不全时先由 Intake 每轮收集一项，不调用无关工具；
- 情景记忆不再跨 `conv_id` 把其他任务的事实当成当前事实。

修复后第一次同集回归：

- 意图准确率 96/100，95% 置信区间约 90.16%–98.43%，Macro-F1 0.8765；
- 结果记录 17/19 通过；
- 调用链 17/18 轮通过；
- Judge 均值：相关性 1.0000、准确性 0.9389、完整性 0.7944、有用性 0.8944；
- 评测执行错误 0。

其中一条未通过是拒绝建单状态未显式写入，已继续修复。另一条是冻结契约与新产品策略不一致：用例要求质量投诉首轮必须由 Resolution 处理，而当前策略刻意使用 Intake 做渐进式信息收集。该用例仍保留为失败，不为追求全绿修改冻结标签。

相同代码再次运行时，意图为 98/100，但结果为 14/19、调用链为 16/18。逐条检查发现两类波动：

- 语义 Judge 将完全符合确定性契约的渐进澄清回复随机评为不完整；
- 生成式 Agent 有时在用户尚未确认“排查完成且故障持续”时提前调用 prepare_service_ticket，导致下一轮工具时序与业务阶段错位。

前者按“Judge 波动”记录，不改用户交互；后者属于真实产品缺陷，已在工具层增加确定性门控。随后只抽取冻结集中的维修确认与换货拒绝两组场景做定向复核，6/6 轮结果和调用链全部通过、执行错误 0；报告 SHA-256 为 `da991464d9ca7133b62fa851f46241cd53aeb33782cd0a5d64d8919b97866243`。由此，项目当前只能报告首次盲测、回归区间和定向修复证据，不能把某一次最高分写成稳定效果。

v2 回归数字只用于证明修复是否有效，不能替换首次盲测数字，也不能外推为线上真实效果。

## 如何复现

版本化数据位于 `后端/evaluation/cases/`。评测器运行真实 Orchestrator，将确定性的调用链断言与语义 Judge 分开记录；开发集和 holdout 基线相互隔离，独立评测不会覆盖开发基线。
