# ResolveFlow 评测集

`resolveflow_v1.json` 是当前 v1.3 可版本化评测集，用于验证消费电子售后 Agent 的意图识别、路由、工具调用、多轮状态、写操作确认和人工升级边界。

`resolveflow_holdout_v1.json` 是独立收口集，包含 100 条平衡意图样本和 15 个对话场景。它不参与本轮 Prompt、路由规则或工具逻辑调参，只用于在开发集冻结后运行一次独立验证。

运行入口：

```json
POST /eval/run
{"dataset":"holdout"}
```

报告中的 `dataset_summary.suite_version` 必须为 `resolveflow-aftersales-holdout-v1.0`，不能与开发集 v1.3 的结果合并计算。

## 当前覆盖

- 意图识别：60 条样本，10 个类别，每类 6 条。
- 对话链路：14 个场景，共 21 轮；包含 10 个单轮和 4 个多轮场景。
- 渐进式澄清：覆盖耳机、电脑和未知设备；信息未就绪时要求 Intake 路由、零诊断工具和单问题组推进。
- 确定性检查：主/协作 Agent、意图、必需/禁止工具、工具顺序与参数、成功状态、问题组契约、结构化状态、任务切换和升级原因；多轮用例在每一轮单独执行检查，不用最后一轮的成功遮盖中间轮错误。
- 写操作负向控制：包含“准备工单后明确拒绝创建”的三轮用例，要求无建单工具调用、无工单号且保留待确认方案。
- 生成质量：LLM-as-Judge 评估相关性、准确性、完整性和有用性，但 Judge 分数不能覆盖确定性检查失败。

## 如何解读

- 意图指标同时报告 Accuracy、Macro-F1、每类 Precision/Recall/F1 及样本数。
- Accuracy 会同时报告 Wilson 95% 置信区间。即使 60 条全部正确，也不应对外表述为“真实业务中稳定 100%”。
- 报告中的 `total` 是“评分结果记录数”，不是数据集样本数。数据集规模以 `dataset_summary` 为准。
- `trajectory_pass_rate` 只统计已配置轨迹契约的轮次，不与 LLM Judge 的四维质量分数混合。
- 这个集合是开发期回归集，并非生产代表性样本。上线前还需要脱敏真实工单、独立人工标注和分布外测试。

## Holdout 使用纪律

1. 先冻结代码与开发集，再运行 holdout；不得根据 holdout 失败直接改标签或放宽断言。
2. 首次完整结果无论高低都保留为独立验证证据。
3. 如果根据失败样本修改系统，原 holdout 即转为回归集；下一次泛化验证必须建立新的、未参与调参的版本。
4. 当前 holdout 由项目团队按产品规则构造，不等同于真实用户分布；后续仍需脱敏工单和独立人工标注。

## 扩充规则

1. 每条用例必须有唯一 `case_id`，并用 `tags` 标记能力或风险。
2. 意图类别保持基本平衡，新增正向例同时补充边界表达、口语表达和容易混淆的负向例。
3. 修复缺陷时先留下会失败的用例，再修正代码；不因为当前系统答不对而改掉标签。
4. 用例集、Judge 提示词和评分配置变化后，`suite_id` 会变化，首次运行只建立新基线，不与旧口径强行比较。
